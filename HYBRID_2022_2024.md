# 2022–2024 analysis with the new hybrid categorization

Branch: `ttH-tH-2022-2024-hybrid`. The old 2022–2023 configs and results are preserved.
These changes prepare the software; they do not establish that the new input production or its systematic recommendations are ready. No production jobs were launched while preparing this branch.

## 1. Fill the actual production inputs

From the flashggFinalFit repository root:

```bash
cp config/hybrid_2022_2024.example.json config/hybrid_2022_2024.local.json
```

Edit the local JSON:

- `tag`: unique production identifier, e.g. `hybrid_2022_2024_v001`. Change it for a fresh production.
- `lumi_fb`: approved luminosity for each era. Existing 2022/2023 numbers are copied from `commonObjects.py`; verify them for the new selected data. The 2024 entry is deliberately unset. If 2024 has sub-eras, replace it with the actual names and populate corresponding beamspot entries.
- `ws_base`: absolute path to the NEW workspace production, containing `<era>/ws_signal/*.root`. Rebuild **all eras** with the hybrid categorization; do not mix old categories or old selections with new ones.
- `data_workspace`: NEW combined data workspace, using the same categories and selected data as all signal eras.
- `categories`: exact new category names. Neither the old count of 16 nor its names are assumed.
- `donors`: one reviewed shape donor for every category, with `process` (e.g. `tth_in`) and `category`. The donor must exist and have a usable shape in each era. Inspect its statistics and fits; the preparation check does not open ROOT datasets to validate this.
- `wv_donor`: explicit process/category pair; retained because the existing fitter still accesses its replacement settings even when fitting the full vertex sample.
- `beamspot_cm`: approved data and MC widths in cm for every era. No automatic reuse of postEE defaults for 2024.

Example donor structure (illustration of syntax, not a production recommendation):

```json
"categories": ["NEW_CATEGORY"],
"donors": {"NEW_CATEGORY": {"process": "tth_in", "category": "NEW_CATEGORY"}},
"wv_donor": {"process": "tth_in", "category": "NEW_CATEGORY"}
```

The template cannot run as delivered: unset values must be supplied. Input paths must be absolute without spaces because existing job writers use unquoted paths.

## 2. Validate and prepare; no fit starts here

```bash
python3 -B prepare_hybrid.py --config config/hybrid_2022_2024.local.json
python3 -B prepare_hybrid.py --config config/hybrid_2022_2024.local.json --write
```

The first command validates the settings and checks workspace paths exist. The second writes a NEW directory, by default `hybrid_runs/<tag>/`. It refuses an existing directory. It creates a copied run configuration, explicit per-era/model Signal configs, background and Trees2WS configs, and stage scripts. It never runs these scripts.

Generated scripts require a CMSSW terminal (`cmsenv`), use absolute paths, run signal jobs sequentially, and write terminal output to a stage log. A `.done` marker prevents rerunning a completed stage; inspect incomplete output before retrying. Both DCB and SoG use the existing fit settings: full vertex sample, `MHPolyOrder 0`, and diagnostic plots. SoG retains the existing RV-based fTest prescription; this is not changed here.

`FINALFIT_RUN_CONFIG` is exported by each generated script. It supplies luminosities and the new hybrid replacement map without modifying old-production settings. Use the **copied** `hybrid_runs/<tag>/run_config.json` with subsequent manual commands, so they use exactly the same settings.

## 3. Folder-by-folder workflow

| Directory | New-production action |
|---|---|
| Trees2WS | Reconvert all 2022, 2023 and 2024 ntuples with the hybrid selections and matching weights/corrections. The generated `trees2ws_config.py` copies the existing branch/systematics schema; verify branches and variations in the new ntuples before using it. `trees2ws.py --year` already accepts 2024. The preparer starts from completed workspaces; it does not guess ntuple file lists or execute conversion. |
| Signal | Generated `signal_DCB_<era>.sh` and `signal_SoG_<era>.sh` use the NEW category list, approved beamspot widths and explicit donors. Results live in `Signal/outdir_<tag>_<era>_<model>/`. Inspect optimizer, boundaries, weights, and shape diagnostics before packaging. |
| Background | Generated `background_config.py` uses the new data workspace, categories, 13.6 TeV and the sum of selected-era luminosities. `background_command.sh` generates official background jobs with `--printOnly`; inspect them and execute sequentially using the command below. This remains the existing data-driven continuum PDF/envelope fit. The upstream hybrid categorizer does not replace it. |
| Datacard | Runners accept `--years` and `--stat-only`. Manifests record the era list/systematic mode, and card building checks both match the selected yield run. Pruning stays at 0.1% of category true yield per component. |
| Combine | Generated `workspace_DCB.sh`/`workspace_SoG.sh` print a no-write workspace-build preview with the existing `r_2D_fiducial` model. Add `--run` to the displayed Python command only after reviewing the card. No category aliases with old hardcoded four-category selections are used. Subsequent scans/significance/impacts need new workspaces and matching freshly generated Asimov data; old snapshots/toys are not reused. |
| Plots | Generated `plot_DCB.sh`/`plot_SoG.sh` use the configured eras/categories and packages. Signal overlays now support 2024. Old static category translations and old plotting summaries must be regenerated; the new runners use actual category names. |
| commonTools | Luminosities are loaded explicitly from the copied run configuration. Internal object naming remains `13TeV` for compatibility; this change does not alter the existing 13.6 TeV cross-section prescription. |

Run one stage at a time, for example:

```bash
# From the repository root, after cmsenv:
bash hybrid_runs/hybrid_2022_2024_v001/signal_DCB_2022preEE.sh
# Review it, then run the equivalent script for each remaining era, including 2024.
bash hybrid_runs/hybrid_2022_2024_v001/package_DCB.sh
```

For SoG, replace DCB with SoG. Never run two jobs that share a Signal extension simultaneously; the official driver also uses a temporary `Signal/config.py`.

Prepare background jobs and run them **sequentially** after checking them:

```bash
bash hybrid_runs/hybrid_2022_2024_v001/background_command.sh
# Inspect Background/outdir_hybrid_2022_2024_v001/fTestParallel/jobs/*.sh first.
for job in Background/outdir_hybrid_2022_2024_v001/fTestParallel/jobs/*.sh; do
  bash "$job" || break
done
```

Check background logs/output files before proceeding. A successfully generated job wrapper is not a fit-quality check.

Then:

```bash
bash hybrid_runs/hybrid_2022_2024_v001/yields_DCB.sh
bash hybrid_runs/hybrid_2022_2024_v001/datacard_DCB.sh
bash hybrid_runs/hybrid_2022_2024_v001/workspace_DCB.sh  # Preview only
bash hybrid_runs/hybrid_2022_2024_v001/plot_DCB.sh
```

Packages, yield runs, cards and plots are under `hybrid_runs/<tag>/`. Signal/background outputs keep their official `outdir_<tag>...` layout. All are ignored by Git. No global run-all command starts an unreviewed full fit.

## 4. Stat-only first, systematics after review

Preparation defaults to **stat-only**: signal fitting uses `--skipSystematics`, no photon-systematics stage is run, yields omit systematic extraction, and cards omit systematic nuisance definitions. Background discrete indices and continuous background parameters remain part of the fit; stat-only is not equivalent to fixing the background. MC-stat nuisance creation remains off, matching the previous runner.

For a later systematic production, first review the 2024 photon scale/resolution prescription and correlations, luminosity components, b-tagging/other weights, available migration variations, missing PDF weights, capping and beamspot corrections. Some 2024 luminosity uncertainty entries already exist in `Datacard/systematics.py`; their presence is not validation of the full 2024 prescription. If sub-era names are used, those uncertainty dictionaries also require the approved mapping.

After review, add `"systematics_reviewed": true` to the local configuration, choose a **new tag**, and prepare with `--with-systematics`. This enables the existing five photon variations and existing datacard systematic scheme; it does not derive new recommendations or verify all nuisance coverage automatically. The theory JSON process lookup now strips all configured era suffixes, including 2024.

## 5. What was checked

Python/shell syntax, explicit configuration validation, rejection of missing values and existing output folders, generated commands, era/mode agreement, and 2024 process-name lookup can be checked without running physics fits. Full ROOT input-content checks, correction validation, new fit quality and statistical results require the actual hybrid production. Official README files are unchanged.
